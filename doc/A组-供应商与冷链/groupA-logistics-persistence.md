## 实现与事务边界

- `OracleGroupALogisticsExtensionProvider` 默认替代进程内兜底。A 组仓储读取基础发货单，`Log_LogisticsDetails` 保存承运商、外部运单号、温区、预计送达、备注；`Log_LogisticsEvents` 保存轨迹及温度。B 组不直接访问这两张表。
- 登记和追加事件先锁定 `(OrderId, SupplierId)` 的基础发货单，所有写入使用传入事务连接。Provider/仓储不创建、提交、回滚或释放事务。事件更新同时更新基础物流状态。
- `EventId` 为全局唯一键；相同编号及规范化载荷重试返回已有快照，内容或归属不同则拒绝。即使后来状态已推进，原事件仍可重试。B 组不能仅按编号直接返回成功。
- 事件序号按发货单唯一；运单唯一键由规范化承运商标识和运单号计算。数据库约束保护跨进程写入。当前只有存储与供应商维护入口，`GROUP_A` 不等于已接入外部承运商自动回调。
- Oracle 时间列和参数显式使用 `TIMESTAMP(7)`；应用进程时区统一为 `Asia/Shanghai`。真实驱动的精度和并发行为仍需隔离库验收。

## 配置与迁移顺序

1. 先备份并在隔离 schema 中执行根目录的 `database_schema.sql`（SQL*Plus / SQLcl 脚本模式）。它是全量结构脚本，创建 A/B/C 三组共 34 张表及其约束与索引，不含业务数据；其中物流扩展部分为基础表增加 `UQ_LED_ORDER_SUPPLIER`，并创建 `Log_LogisticsDetails`、`Log_LogisticsEvents`。DDL 隐式提交，不可作为可回滚业务事务执行。
2. 对已有同名表核对全部列类型、长度、主外键、检查及唯一约束，确认 `ENABLED / VALIDATED`。全量脚本不会改造已存在的同名表（对已有 schema 重复执行会因对象已存在而报错），部分失败后请先修正原因再重跑。
3. 数据库验收通过后再部署应用。默认 `GroupA:Logistics:Provider=Oracle`，不自动迁移、不在缺表或连接失败时静默退回内存。**未迁移就启动新版本，已有发货单的高级物流读取和发货操作会失败。**
4. 温控配置为 `GroupA:Logistics:ChilledMinimumCelsius`（默认 0）、`ChilledMaximumCelsius`（默认 8）、`FrozenMaximumCelsius`（默认 -18）。应用启动检查冷藏上下限。
5. 只有显式 `Provider=Fallback` 且 `Development` 环境才能使用内存演示；还须提供完整 `GroupB:LogisticsFallback` 配置。Staging/Production 启用 Fallback 会被启动配置校验拒绝。不能以开发模式替代生产迁移。

## 历史数据和异常

- 旧基础单不批量回填或虚构完整历史。首次读取展示带明确描述的基础记录，事件编号从发货单稳定派生。旧单状态可保留，但若缺少实际签收事件，`DeliveredAt` 为空，不把发货时间当签收时间。
- 旧单首次追加事件时，基础记录、缺失元数据和新轨迹在同一事务保存。
- 超过预计送达且未结束的包裹读取时生成稳定的延误提示；读取不写库，该派生事件在下次轨迹写入时同事务保存。**未保存的派生提示不能当作原始承运商退款证据。**
- 温度超限把本次可接受的物流更新记录为 `EXCEPTION`，不能借此签收。恢复运输会清除当前异常标记，但保留原异常轨迹。终态禁止回退。

## 本次验证与尚未完成

12 个新增场景覆盖外部事务归属、提交/回滚、末步失败、服务实例重建、重复/冲突事件、供应商隔离、温控、延误、历史数据、状态校验和 DI 环境限制。与已有场景合计 94 个通过。

模拟仓储只验证顺序事务语义，不证明 Oracle 并发锁、跨进程持久性或真实 FEFO 原子性。尚需隔离库验证：

- 发货、库存批次扣减、扩展元数据、事件和订单状态整体提交/回滚；在最后一步注入失败。
- 两个独立数据库连接同时登记同一包裹、追加同一事件、抢用同一承运商运单，核对没有重复事件或部分数据。
- 杀掉并重启应用进程，轨迹、温度、承运信息、签收时间均保持；真实数据库亚秒时间精度保持。
- 实际供应商登录后追加合法事件；其他供应商、停用账号及非法状态被拒绝；消费者刷新可看到相同已提交轨迹。

本轮没有对共享 Oracle 执行迁移或业务写入；不能据此宣称全部接口联调完成。
