# GroupB 实施计划

## 1. 计划依据

本计划于 2026-07-27 根据以下资料和当前仓库状态制定：

- `tmp/分工.pdf`
- `tmp/生鲜冷链团购分销供应链系统.pdf`
- `tmp/生鲜系统数据库课设要求.pdf`
- `requirement_groupB.md`
- `project_design.md`
- `groupB_ddl.sql`
- `dev-groupB`、远端 `dev-groupA`、远端 `dev-groupC` 的现有实现

GroupB 负责 `Crm_Customers`、`Crm_UserAddresses`、`Crm_MemberLevels`、
`Mkt_Coupons`、`Mkt_CouponRecords`、`Crm_PointLogs`、`Biz_Orders` 和
`Biz_OrderDetails` 8 张核心表，并为月度定级维护 `Crm_MemberLevelHistories` 扩展表；
核心业务为订单事务、供应商拆单、会员等级、优惠券和积分闭环。

## 2. 当前基线与决策

### 2.1 已有能力

- ASP.NET Core MVC、Dapper、Oracle 三层架构已经建立。
- GroupB 的 8 张表已有独立 DDL 草案和对应的主要模型。
- 已有订单、消费者、优惠券、积分仓储以及基础 Service。
- 已有下单演示页和对外 `IOrderService`、`ICustomerService`、`ICouponService`。
- 项目在 .NET 10 下可以编译。

### 2.2 已确认的问题

- 原 Repository 在收到外部事务后仍创建新连接，无法保证 Oracle 事务原子性。
- 下单页面和明细仍为硬编码演示数据，金额由客户端模型传入，不能作为真实业务入口。
- 优惠券只做了部分门槛校验，未在下单事务内完成归属、有效期、状态和核销闭环。
- 会员等级仅能查询，尚未在累计消费变化后自动更新。
- 地址、消费者、优惠券、订单查询和详情等页面及 CRUD 尚未完成。
- 暂无自动化测试项目，也未在可控 Oracle 测试库执行集成测试。

### 2.3 主键类型差异

数据库设计 PDF 约定主键为 `VARCHAR2(36)`。截至 2026-08-08，远端 A/C 组的商品、
供应商和团长标识已经使用字符串 GUID，B 组已同步将 `ProductId`、`SupplierId`、
`PromoterId` 及对应跨组 DTO 改为字符串，避免联调时发生数值解析和状态漂移。
B 组自有 8 张核心表及定级历史扩展表的主键和内部外键现已全部迁移为 `VARCHAR2(36)`；服务端新增记录使用
32 位 GUID 字符串，Vue、MVC、REST API 和跨组契约均不再进行数值解析。

### 2.4 分支与提交策略

- 按团队规范继续使用 `dev-groupB`，不向 `main` 直接提交。
- 每阶段形成一个边界清晰的提交并推送 `origin/dev-groupB`。
- 每阶段完成后更新本计划、`GroupB-progress.md` 和对应阶段总结，然后停止。
- `tmp/` 仅保存原始参考材料和阅读中间文件，不提交到仓库。

### 3.1 阶段 2 落地决策

- 客户端下单请求只允许提交消费者、地址、优惠券记录、商品 ID 和数量，不接收价格、
  商品名、供应商、金额、积分或订单状态。
- B 组通过内部 `IGroupAInventoryGateway.CheckAvailabilityAsync` 调用 A 组公开商品、库存和供应商服务；
  发货时再由 A 组冷链服务在 B 组事务中执行真实行锁与 FEFO 扣减。
- 生产运行时使用 `GroupAInventoryServiceAdapter`；测试项目使用 Fake 隔离 Oracle。
- 优惠券记录和券模板在事务内使用 `FOR UPDATE` 锁定，并通过带 `Status = 0` 条件的更新
  进行核销，防止同一张券并发重复使用或校验期间模板状态漂移。
- 消费者记录在积分计算前锁定，避免并发订单互相覆盖积分余额。
- 同商品请求会在服务端合并；订单明细按库存服务返回的供应商形成拆单结果。
- 运费由 A 组真实冷链报价服务计算。

### 3.2 阶段 3 落地决策

- 消费者创建只接收基础资料和原始密码，密码通过 ASP.NET Core
  `PasswordHasher<CrmCustomer>` 生成哈希；积分、累计消费和会员等级不允许页面直接修改。
- 手机号码作为消费者唯一业务标识，DDL 增加唯一约束，Service 在创建前给出友好重复提示。
- 地址新增、编辑、删除和设默认均先锁定消费者行，同一消费者的地址变更由 B 组事务串行化。
- 第一条地址自动成为默认地址；删除或取消当前默认地址时自动选择其他地址顺延。
- DDL 使用 Oracle 函数式唯一索引约束 `IsDefault = 1` 的地址，形成 Service 和数据库双重保护。
- 下单累计消费更新后，在同一事务内查询最高符合的 `MinSpent` 等级并写回
  `MemberLevelId`；本次订单积分仍按下单前已生效等级计算。
- 每位消费者对同一券模板限领一张。领券依次锁定消费者和券模板，检查活动窗口、库存和
  重复领取，再以条件更新扣库存并写用户券；任一步失败都回滚。
- 优惠券中心同时展示当前活动模板和消费者未使用、未过期的可用券记录 ID，供下单选择。

### 3.3 阶段 4 落地决策

- B 组订单状态统一使用 `OrderStatus`，持久化为 `PENDING_PAYMENT`、`PAID`、`SHIPPED`、
  `COMPLETED`、`CANCELLED`、`REFUNDING`、`REFUNDED` 七个字符串代码；状态机只开放已支付→已发货、已发货→已完成和
  已支付→已取消。
- 状态更新必须先锁定消费者和订单，再以旧状态作为 `UPDATE` 条件；Controller 和
  Repository 不提供绕过状态机的无条件状态修改入口。
- 下单保存收件人、电话和完整地址快照，订单详情不因消费者之后修改地址而漂移。
- 冷链运费通过 `ILogisticsService.CalculateFreightAsync` 获取，不在 B 组实现 A 组算法；
  生产实现调用 A 组 `IColdChainLogisticsService`。
- 已支付→已发货时，由 `ILogisticsService.CreateShipmentAsync` 在 B 组事务中创建 A 组
  物流记录；供应商履约状态通过只读契约查询，不在 B 组重复写物流表。
- 已发货→已完成时，在同一事务调用 `ICommissionService.RegisterCompletedOrderAsync`，
  向 C 组传递可信的订单、消费者、团长和佣金基数快照。
- 已支付未发货订单取消时不触碰尚未扣减的 A 组库存；B 组归还用户券、扣回订单奖励积分、
  冲减累计消费和重新定级，任一步失败均回滚。
- A 组库存/物流和 C 组支付/佣金/团长/退款均已接入现有实现；生产 DI 不再注册 Dummy。

## 4. 阶段执行规则

每个阶段依次执行：

1. 复核需求、远端接口与上阶段遗留问题。
2. 更新计划和进度文档。
3. 完成功能和必要的数据库脚本。
4. 执行编译、自动化测试、静态检查；涉及数据库时记录测试环境和结果。
5. 编写阶段总结，明确已完成、未完成和下一阶段入口。
6. 仅暂存本阶段范围内文件，提交并推送 `dev-groupB`。
7. 停止，等待用户继续下一阶段。

## 5. 主要风险

- Oracle 测试库的版本、账号权限和现有表结构尚未核实，DDL 与集成验证可能受环境影响。
- A 组当前代码同时实现了订单能力，与 GroupB 的职责有重叠，正式合并前需要冻结跨组接口。
- C 组支付审计日志使用独立连接，外层订单事务回滚时存在日志先提交风险；由 C 组修正。
- 下单到发货之间库存可能变化；A 组发货接口以行锁和 FEFO 扣减做最终裁决，失败时 B 组订单保持已支付。
- `appsettings.json` 当前包含固定连接配置；在最终交付前应迁移到开发机 Secret 或环境变量，
  并更换已暴露的凭据。
