# 生鲜冷链团购分销供应链系统

## 团长与管理员模块设计报告

---

## 1. 引言

本系统为数据库课程设计项目「生鲜冷链团购分销供应链系统」。平台围绕生鲜冷链商品的团购分销场景，划分四类角色入口：

| 角色 | 技术形态 | 入口 |
| --- | --- | --- |
| 消费者 | Vue 3 SPA（`ClientApp/`） | `/app/` |
| 团长 | ASP.NET Core MVC Razor | `/Promoters/Dashboard` |
| 供应商 | ASP.NET Core MVC Razor | `/Goods/MyGoods` |
| 管理员 | ASP.NET Core MVC Razor | `/Admins/Dashboard` |

团长是分销链路的中间层：从供应商货盘中挑选商品入团、自行定价与撰写带货介绍，消费者关注团长后按其货盘下单；订单签收后产生佣金，过退款期后可提现。管理员是平台治理层，按职责拆成账号、财务、日志、商品四类，分别负责入驻审核、资金审核、操作审计与平台货品管理。

本文档依据当前仓库实现，说明团长、管理员两端的业务逻辑、前端页面结构、接口约定，以及二者与消费者端、订单履约、财务结算的衔接关系。

---

## 2. 总体架构

### 2.1 分层结构

团长与管理员模块同属 C 组（分销结算与后台治理），采用经典三层：

```
Views（Razor 门户） / Controllers/Api（消费者 REST）
        │
Controllers（Account / Promoters / Admins）
        │
Services（PromoterService / SystemAdminService / WithdrawalService
          / CommissionService / RefundService / TableLogService）
        │
Repositories（Dapper + Oracle） + IUnitOfWork
        │
Oracle 表：CRM_PROMOTERS、CRM_PRODUCT_ENTRIES、CRM_PCR、
           FIN_WITHDRAWALRECORDS、FIN_PROCOMRECORDS、
           SYS_USERS、LOG_AUDITTRAILS …
```

关键约定：

- 团长门户、管理后台均为服务端渲染 MVC，会话保存在 ASP.NET Session（30 分钟空闲超时）。
- 消费者端不直接访问团长/管理员 MVC 页面，而是通过 REST API 读取团长货盘、关注关系与评价摘要。
- 写操作普遍自建事务，关键状态变更写入 `LOG_AUDITTRAILS`，便于日志管理员审计。

### 2.2 角色协同关系

```
供应商上架货物（Inv_Goods.ACTIVE）
        │
团长搜索并入团（CRM_PRODUCT_ENTRIES）
        │
消费者浏览 / 关注团长 / 按下单货盘购买
        │
订单签收 → 一段结算（待结算佣金）→ 14 天后二段激活（可提现）
        │
团长申请提现 → 财务管理员审核打款
        │
消费者退款 → 财务管理员审核 → 佣金/积分对称回滚
```

账号管理员控制「谁能进来」：团长、供应商、管理员的注册审核与启禁用。财务管理员控制「钱怎么走」：提现、退款、支付流水。日志管理员只读审计。商品管理员复用 A 组平台级货品与物流页面。

## 3. 团长模块

### 3.1 业务定位

团长不是仓储方，也不直接履约发货。其核心职责是：

1. 以社区分销身份入驻平台，获得邀请码与基础佣金比例。
2. 从供应商货盘中挑选（商品 × 供应商）组合入团，设置团长售价与图文介绍。
3. 吸引消费者关注；消费者下单时订单绑定该团长。
4. 在订单完成后获得基础佣金与阶梯奖励，过退款期后提现。

对应数据主体：

| 表 | 用途 |
| --- | --- |
| `CRM_PROMOTERS` | 团长档案、余额、佣金比例、收款账户、状态 |
| `CRM_PRODUCT_ENTRIES` | 入团货盘：（团长，商品，供应商）三元组 |
| `CRM_PCR` | 消费者关注团长关系 |
| `FIN_PROCOMRECORDS` | 按单佣金记录（待结算 / 已结算 / 已退款） |
| `FIN_WITHDRAWALRECORDS` | 提现申请与审核结果 |

### 3.2 账号生命周期

#### 注册

入口：`Account/RoleSelect` → 团长登录页 →「点击注册新账户」→ `Account/PromoterRegister`。

校验规则：

- 登录账号不可重复。
- 两次密码一致；密码以 SHA-256 后 Base64 入库。
- 系统生成 8 位邀请码、团长编号 `PRO_` + GUID。
- 初始基础佣金比例 **3%**，余额与销售额均为 0。
- 状态置为 **`Pending`**，须账号管理员审核后才能登录。

管理员在「账号新增」中直接创建团长时，可指定佣金比例，状态直接生效，无需再走注册审核。

#### 登录

入口：`POST /Account/Login?role=团长`。服务层 `PromoterService.LoginPromoter` 校验：

| 状态 | 登录结果 |
| --- | --- |
| `Pending` | 拒绝：「账号尚未审核，请耐心等待」 |
| `Disable` | 拒绝：「账号未审核通过」 |
| `Frozen` | 拒绝：「账号已被禁用」 |
| `Enable` | 成功，写入 Session `PromoterId` / `PromoterName`，跳转工作台 |

未登录访问团长页面时，`PromotersController.EnsureLoggedIn()` 重定向到团长登录页。

#### 启禁用

账号管理员在「账号管理」中仅允许 `Enable` ↔ `Disable` 互转；`Pending` 必须先走注册审核。禁用后团长无法登录，其已入团商品对消费者端也不再作为可关注对象（列表接口只返回 `Enable`）。

### 3.3 商品入团与定价

入团单位不是「商品」，而是 **（商品 × 供应商）**。同一商品可由多家供应商供货，团长分别入团、分别定价。

#### 搜索与上架

`GET /Promoters/ProductListing?keyword=`：

- 无关键词：只展示搜索框与当前已上架列表。
- 关键词匹配供应商名称/ID：列出该供应商全部货物。
- 关键词匹配商品名称：列出所有供应该商品的（供应商 × 商品）组合。

搜索调用 A 组 `ISupplierService.SearchSupplierProductEntriesAsync`。入团前校验 `Inv_Goods.Status == ACTIVE`，供应商已下架则不可入团。

#### 定价规则

团长售价须落在推荐价附近的安全区间，避免恶性低价或虚高：

\[
\lvert 团长价 - 推荐价 \rvert < \frac{\lvert 推荐价 - 供应商报价 \rvert}{2}
\]

未填写时默认取推荐价。若推荐价等于报价（允许差为 0），则团长价必须等于推荐价。入团与事后改价共用同一规则，由 `PromoterService.AddProductEntryAsync` / `UpdateEntryPriceAsync` 校验。

#### 图文带货介绍

入团时默认复制供应商商品文字。团长可在独立详情页用富文本编辑器撰写「推文」：标题 + 多段文字/图片。内容以 JSON 文件落在 `wwwroot/uploads/promoter-desc/`，数据库 `PROMOTERDESC` 只存相对路径。本地图片上传到 `wwwroot/uploads/promoter-img/`（扩展名校验，单张不超过 5MB）。

消费者端展示优先级：团长图文介绍 → 若无则兜底供应商文字。供应商下架后，团长端列表仍可见并标注「已下架」，消费者端目录不再展示该条目。

### 3.4 消费者绑定（关注）

关注关系存于 `CRM_PCR`，一对多：一名消费者可关注多名团长。

- 消费者端：`POST/DELETE /api/customers/{customerId}/following/{promoterId}`。
- 团长端：「我的消费者」页列出已绑定用户。
- 下单时购物车按团长拆单，`Biz_Orders.PromoterID` 记录归属团长，作为后续计佣依据。

### 3.5 佣金结算

佣金不在下单瞬间入账，而是与订单履约、退款窗口绑定，分为两段。

#### 一段结算：订单完成后登记

订单签收完成后，B 组 `OrderService` 调用 `ICommissionService.RegisterCompletedOrderAsync`：

1. 累计销售额加上本单商品金额。
2. 按**结算前**的基础佣金比例计算本单基础佣金：  
   `CommBaseAmount = BaseCommissionRate × 实付金额`。
3. 若累计销售额跨过等级阈值，更新下一单适用的佣金比例（本单仍用旧比例）。
4. 阶梯奖励：累计销售额每跨过一档发放对应奖金，一单跨多档可叠加。
5. 总佣金写入团长 **待结算余额** `PendingBalance`，并插入 `FIN_PROCOMRECORDS`，状态 `Pending`，预计结算日 = 签收日 + **14 天**。

等级与比例（与累计销售额挂钩）：

| 等级 | 累计销售额 | 基础佣金比例 |
| --- | ---: | ---: |
| 青铜 | &lt; 1,000 | 3% |
| 白银 | ≥ 1,000 | 4% |
| 黄金 | ≥ 3,000 | 5% |
| 钻石 | ≥ 5,000 | 8% |

阶梯奖励（部分档位）：跨过 1,000/2,000 各奖 50；3,000/4,000 各奖 150；5,000 奖 750；其后 6,000–10,000 另有对应档位。退款导致销售额跌破档位时，按同一张表对称撤销奖励。

#### 二段结算：过退款期后激活

后台托管服务 `GroupC_CommissionSettlementWorker` 每小时扫描到期且仍为 `Pending` 的佣金记录，调用 `ActivatePromoterMoney`：待结算余额转入 **可提现余额** `CurrentBalance`。

#### 退款回滚

财务管理员通过退款后，`RefundService` 按退款比例回滚基础佣金，并按销售额跌档撤销阶梯奖励，同时回退等级佣金比例。保证「发放」与「撤销」使用同一政策表。

### 3.6 提现

团长须先绑定微信 / 支付宝 / 银行卡之一，账户格式由 `PromoterPayAccounts` 校验。申请规则：

- 金额 &gt; 0，且不超过可提现余额。
- 同一时刻只允许一笔 `Pending` 提现。
- 申请成功：可提现余额减少，**冻结金额**增加，写入提现记录。

财务管理员审核：

- **通过**：冻结金额扣除，记录打款时间，状态 `Approved`。
- **驳回**：必须填写原因；冻结金额解冻并退回可提现余额，状态 `Rejected`。

技术栈：Razor Views + Bootstrap 5 + `promoter-portal.css`。统一布局 `_PromoterLayout.cshtml`：左侧固定侧栏 + 右侧主内容。侧栏底部 `PromoterSidebar` 组件展示当前团长姓名与退出入口。

#### 交互与视觉要点

- 工作台采用「欢迎横幅 + 指标卡片网格 + 内容卡片」结构，与管理后台共用同一套 portal 视觉，通过 `role-promoter` / `role-admin` 区分主题色。
- 写操作使用 Anti-Forgery Token；成功/失败以 TempData + `_Alerts` 部分视图提示。
- 搜索上架采用 PRG（Post-Redirect-Get），避免刷新重复提交。
- 图文编辑器为页面内嵌组件 `_RichIntroEditor.cshtml`，图片上传走 Ajax JSON（`UploadPromoterImage`），不刷新整页。
- 头像仅允许系统预置 8 种标识：`cat / rabbit / panda / fox / carrot / broccoli / tomato / corn`，与消费者端头像资源一致。

## 4. 管理员模块

### 4.1 业务定位与种类划分

管理员账号存于 `SYS_USERS`，字段 `ADMIN_KIND` 将权限拆成四类。登录时必须选择与注册时一致的种类，否则拒绝登录。Session 写入 `AdminId`、`AdminName`、`AdminKind`。

| 种类代码 | 名称 | 登录后落点 | 职责边界 |
| --- | --- | --- | --- |
| `ACCOUNT` | 账号管理员 | `/Admins/Dashboard` | 注册审核、账号新增、启禁用、团长佣金比例 |
| `FINANCE` | 财务管理员 | `/Admins/Dashboard` | 提现审核、退款审核、支付/退款流水查询 |
| `LOG` | 日志管理员 | `/Admins/OperationLogs` | 仅操作日志查询 |
| `PRODUCT` | 商品管理员 | `/Goods/AdminIndex` | 平台级物品、货物、定价规则、运费模板与溯源 |

侧栏按种类渲染不同菜单：日志管理员只有「操作日志」一项；商品管理员导航复用 A 组 `Goods / Products / Prices / ColdChainLogistics`；财务与账号管理员各自工作台 + 业务菜单。

注册同样需审核：新管理员状态为 `Pending`，由**已启用的账号管理员**审核通过后，状态变为可登录（`Enable` / `Enabled`）。

### 4.2 账号管理员业务逻辑

#### 注册审核

页面 `AccountReview` 同时列出三类待审对象：

1. **团长**：通过 → 状态 `Enable`；拒绝 → 不可登录。
2. **供应商**：通过 → `Active`；驳回须填原因 → `Rejected`。
3. **管理员**：通过后该账号可按所选种类登录；驳回可填原因。

审核写操作日志，操作者取当前 Session 中的管理员名。

#### 账号新增

管理员代建团长或供应商，**免审核直接生效**。团长默认佣金比例 3%，可在表单中修改（0～1 的小数，如 0.03 表示 3%）。

#### 账号管理

- 团长：启用/禁用；调整基础佣金比例。
- 供应商：`Active` ↔ `Disabled`（驳回账号可重新启用为 `Active`）。
- 管理员：启用/禁用；不可误操作导致系统无人可审（页面传入当前 `AdminId` 供前端区分自身）。

团长 `Pending` 不允许在本页直接启用，必须回到注册审核，避免绕过入驻材料核验。

### 4.3 财务管理员业务逻辑

#### 提现审核

列表来自 `WithdrawalService.GetPendingWithdrawalsAsync`。通过即视为打款完成（`TransferTime = AuditTime`），扣减冻结金额；驳回必须填写原因并解冻。工作台汇总待审笔数与合计金额，并预览最近 5 笔。

#### 退款审核

消费者在 C 端提交退款后进入待审。管理员：

- **通过**：执行资金回滚（佣金、积分）、订单状态变更；提示「退款已通过，资金回滚已执行」。
- **驳回**：必须填写原因，不触达资金。

#### 支付流水

`PaymentRecords` 支持按起止日期（结束日含当天）、订单号、支付状态、退款状态组合筛选，同时展示支付流水与退款记录，满足对账需要。

### 4.4 日志管理员业务逻辑

`OperationLogs` 查询 `LOG_AUDITTRAILS`，筛选条件：时间区间、表名、操作类型、操作者。表名下拉来自已有日志去重。团长注册、佣金变动、提现冻结、供应商状态变更等写路径都会落日志，本页为只读审计入口。

### 4.5 商品管理员业务逻辑

商品管理员不在 `AdminsController` 内实现货品 CRUD，而是登录后进入 A 组页面，并由 `[RequireAdmin]` 保护：

- 全部货物 `/Goods/AdminIndex`
- 物品管理 `/Products`
- 定价规则 `/Prices`
- 计算运费 / 发货记录 / 精准溯源 / 运费模板 `/ColdChainLogistics`

其它种类管理员若误入这些地址，过滤器会将其送回各自 `Admins/Dashboard`。平台级下架物品会连带所有供应商该货物下架，进而影响团长入团可见性。

## 5. 团长与管理员的协同流程

### 5.1 入驻闭环

```
团长填写注册表单
    → CRM_PROMOTERS.Status = Pending
    → 账号管理员工作台待办 +1
    → AccountReview 通过 / 拒绝
    → Enable 后方可登录上架；Disable/拒绝则无法进入门户
```

管理员代建路径跳过 Pending，适合课程演示或内部签约团长。

### 5.2 佣金与提现闭环

```
消费者关注团长并下单（订单带 PromoterID）
    → 签收完成：一段结算，PendingBalance ↑，佣金记录 Pending
    → 14 天定时任务：CurrentBalance ↑，佣金记录已结算
    → 团长绑定收款账户并申请提现：CurrentBalance ↓，FrozenAmount ↑
    → 财务管理员审核
         ├─ 通过：FrozenAmount ↓，提现 Approved
         └─ 驳回：FrozenAmount ↓，CurrentBalance 恢复
```

若在 14 天内发生退款且财务审核通过，则在激活前从待结算余额扣回，避免「已提现再追回」的复杂对账。

### 5.3 货盘与商品治理闭环

```
商品管理员维护平台物品与上下架
    → 供应商维护自家货物 ACTIVE/下架
    → 团长只能入团 ACTIVE 货物
    → 供应商事后下架：团长端标注已下架，C 端目录隐藏
```

账号管理员调整团长佣金比例后，立即作为后续新单的计佣基数；历史未结订单仍按其生成时的记录金额结算。

### 5.4 审计闭环

注册、状态变更、余额冻结/解冻、佣金比例修改、供应商状态变更均写入 `LOG_AUDITTRAILS`（表名、操作类型、旧值/新值、操作端、操作者）。日志管理员按表与时间追溯，不参与业务审批，形成职责分离。

## 6. 关键数据与状态机

### 6.1 团长状态

```
        注册                 审核通过
（无） ──────► Pending ──────────────► Enable
                  │                      │
                  │审核拒绝              │账号管理禁用
                  ▼                      ▼
               Disable ◄────────────── Enable
                             重新启用
```

登录仅 `Enable` 可通过。

### 6.2 提现状态

```
申请 ──► Pending ──审核通过──► Approved（已打款）
              │
              └──驳回──► Rejected（资金解冻）
```

`Approved` 后允许再次发起新的提现；`Pending` 未结束时禁止并发申请。

### 6.3 佣金记录状态

订单完成后为 `Pending`（待过退款期）；到期激活为已结算；退款冲抵后体现退款金额并可能变为已退款类状态。团长「佣金明细」页按状态筛选。

### 6.4 团长资金三账户

| 字段 | 含义 | 增减时机 |
| --- | --- | --- |
| `PendingBalance` | 待结算佣金 | 一段结算增加；激活或退款回滚减少 |
| `CurrentBalance` | 可提现余额 | 二段激活增加；申请提现减少；提现驳回加回 |
| `FrozenAmount` | 审核中提现金额 | 申请增加；通过或驳回减少 |

工作台「资产合计」= 三者之和，避免团长误以为待结算资金可立即提走。

## 7. 安全与实现要点

1. **会话隔离**：团长用 `PromoterId`，管理员用 `AdminId` + `AdminKind`，供应商用 `SupplierId`，互不复用。
2. **密码**：SHA-256 + Base64，不明文存储。
3. **CSRF**：团长/管理员表单 POST 使用 Anti-Forgery Token。
4. **权限分流**：管理员种类在登录时绑定，侧栏与 Dashboard 按种类裁剪；商品级接口另用 `[RequireAdmin]`。
5. **事务**：注册、提现申请/审核、佣金激活、退款回滚均在 `IUnitOfWork` 中提交或回滚，避免余额与流水不一致。
6. **幂等与防重**：提现「已有 Pending 则拒绝」；关注关系已存在则视为成功；佣金激活按记录扫描，单条失败不影响其它记录。
7. **跨组边界**：团长搜索货盘、校验货物上架依赖 A 组供应商/货物服务；计佣由 B 组订单完成时回调 C 组 `ICommissionService`；消费者关注与货盘展示走 REST，团长门户本身不暴露给 C 端 SPA。

## 8. 与消费者前端的衔接（团长侧可见部分）

消费者 SPA 不实现团长工作台，但团长模块的产出直接决定 C 端内容：

| C 端页面 | 依赖的团长能力 |
| --- | --- |
| 首页 / 关注页 | `GET /api/promoters`、关注 API |
| 团长主页 `LeaderDetailView` | 团长资料、带货列表、评价摘要 |
| 团长推文 `PromoterIntroView` | 图文介绍 API |
| 结算 `CheckoutView` | 购物车按 `leaderId` 拆单，订单写入 `promoterId` |
| 订单列表 | 展示所属团长并链到团长主页 |

因此团长「商品上架 + 定价 + 推文」本质上是 C 端货盘的内容管理系统；管理员「审核 + 启禁用」则控制这些内容是否对公网可见。

## 9. 小结

团长模块把「选品、定价、内容、粉丝、佣金、提现」收束在同一门户内，用（商品 × 供应商）入团模型和两段式佣金保证冷链售后窗口内的资金安全。管理员模块按账号 / 财务 / 日志 / 商品拆权，避免单一超级账号同时改身份、改资金、改货品。两端均以 MVC 门户服务课程演示与运营操作，同时通过一组清晰的 REST 接口把团长货盘与关注关系交给消费者 SPA，形成完整的生鲜冷链团购分销闭环。
